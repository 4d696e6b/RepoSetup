# 0.4.0 offline-only milestone acceptance

Owner-selected scope: **offline-only**, 2026-10-10. This amendment governs the
completion of Milestones I and J. It changes milestone scope, not historical
results, executor authority, model qualification or release status.

## Milestone I — offline functional qualification

Required evidence:

- Five frozen types/UI/API/cross-module/security fixtures discriminate their
  seed, reference and advertised mutations using independent public/holdout checks.
- Whole-phase, compiled fixed and compiled routed diagnostic paths retain all 75
  simulated failure slots. Vetted successful and context/repair blocks retain
  actual scoped changes, real tools, independent terminal observations and durable
  task/final-phase acceptance. Missing comparative trials and unknown provider
  usage remain explicit; every report keeps `qualification: false`.
- Core/provider/state/repair regressions, compatibility, dry-run and packed aliases
  pass. Installed portable compilation and unchanged project/privacy guards pass
  on Linux/macOS; Windows verifies the unsupported task profile without effects.
- Real-tool concrete verification and frozen-fixture suites pass for Linux x64
  and macOS arm64 on Node 24. Source, runtime, lockfile, tool/fixture identities
  and installed artifact hashes must be recorded. Individually identified
  development results may support this milestone; they cannot be combined into
  a same-source frozen release repeat.
- Production capability profiles remain unconfirmed and production routing fails
  closed. Simulated catalogs remain test-only. No credential or paid call is needed.

These checks establish implemented behavior and failure accounting. They establish
no remote schema/account support, model quality, comparative speed/cost savings or
production capability/native effort qualification. A simulated accepted result is
an actual local implementation acceptance, not independent evidence that a model
can generate that implementation.

## Milestone J — offline delivery preparation

Required evidence:

- I's amended offline conditions pass, with unresolved limits recorded clearly.
- Help, README, changelog, user guide, compatibility/no-migration notes and exact
  unsupported behavior describe the implemented development commands.
- Source safety, dependency licenses/advisories, provider boundary and support
  limits are reviewed; applicable build/typecheck/lint and packed/platform checks pass.
- Identify the unchanged-version diagnostic packed artifact and its provenance.
  Keep the reviewable branch/draft PR and committed status evidence available.

Completion means **offline implementation and delivery preparation complete**.
It does not mean a versioned 0.4.0 candidate, qualified production model service,
release, publication, or completed stability soak. Existing commands/configs remain
compatible; no website, system software or package version change is authorized.

## Deferred prerequisites before a managed/versioned release

The original live provider/profile smoke, 75 real comparative model trials and
production capability/native effort evidence remain unverified. They move outside
these offline milestones and remain prerequisites for qualifying managed production
support. Original finite spending authorization is not enlarged or renewed.

Intentionally selecting a candidate version, freezing that candidate/artifact,
three consecutive complete qualifications of that same candidate, and seven
calendar days without an open P0/P1, data-loss or security defect remain release
prerequisites. Their clock has not started. Merge/tag/publication remain separate
actions. This amendment neither passes nor removes these release gates.
